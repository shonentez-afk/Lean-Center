## LC8.1: первичный вход администратора

Предусмотреть начальную учётную запись до открытия портала. Предложенный логин — admin, настраиваемый серверной переменной LC_BOOTSTRAP_ADMIN_LOGIN; пароль задаёт владелец при развёртывании через секрет Amvera LC_BOOTSTRAP_ADMIN_PASSWORD. Без заводского пароля и публичной регистрации.

При первом запуске чистого защищённого хранилища до готовности HTTP API атомарно создать ровно одну начальную административную учётную запись с постоянным account_id, стойким salted hash, подтверждённым системным назначением в едином справочнике ролей и явными административными полномочиями. Для работы со всеми бизнес-модулями первому администратору явно назначить также профиль управляющего в выбранной области предприятия; не выдавать полномочия директора и согласующих автоматически. Начальную системную идентичность можно создать до заполнения справочника людей; после входа привязать её к существующему сотруднику с сохранением account_id и истории. Не создавать фиктивную кадровую запись, сертификат или подпись. До привязки не разрешать действия от имени сотрудника. Если начальный секрет отсутствует/не соответствует политике, хранилище повреждено или bootstrap не завершён, защищённый режим не объявляет готовность; оператор получает диагностическое сообщение без секрета, без fallback к старым пилотным токенам. Не уничтожать и не заменять прежние данные.

На demo первый администратор входит сразу, обязательная смена пароля и функции смены/сброса пока отключены по решению владельца. После подтверждённого первого входа исходный bootstrap-секрет можно удалить из Amvera; в постоянном серверном хранилище остаётся только хэш. Повторный запуск/обновление сохраняет существующий аккаунт и полномочия, не создаёт дубль и не меняет пароль даже при изменении переменной. Не запускать повторный bootstrap при удалении/блокировке администратора, восстановлении повреждённой базы или отсутствии уже инициализированного security store. Последнего действующего администратора нельзя заблокировать/лишить административных прав обычным действием. Аварийное восстановление доступа — отдельная будущая процедура, не повторная выдача bootstrap. До запуска документировать вход, резервирование security store и проверку восстановления.

Приёмка: чистый стенд с секретом создаёт администратора и позволяет войти; без секрета не переходит в небезопасный режим; перезапуск и удаление/замена bootstrap-секрета после создания аккаунта не меняют пароль; неверный пароль отвергается; учётные записи и права сохраняются; секрет не попадает в UI, логи, клиентский экспорт или GitHub; повреждённое/пропавшее существующее хранилище не приводит к созданию нового админа. # LC8 — персональный многопользовательский Центр TWI (проект требований)

Основание: пользователь просит добавление разных пользователей, персональные уведомления в верхней панели, email и полноценное согласование СОП. Нумерация LC8 предложена для отдельного пакета; LC7.5/LC7.6 (инструкция/приёмка) не отменяются. LC7.4.5 прошёл полный CI 45878973539; LC7.4.6 меняет только индикацию/защиту закрытия. Ни одно требование ниже не считать реализованным до отдельной приёмки.

## Исходное состояние и границы

Текущий пилот — LC_PILOT_USERS (JSON/HEX1, 1–20 учётных записей, editor/viewer), весь снимок SQLite v17 передаётся каждому вошедшему пользователю. Бизнес-роли и назначения сотрудников (person, business_role, role_assignment, person_assignment) уже существуют, но не являются правами доступа. Существующие document_revision/document_approval и переходы submit/approve/return/effect/withdraw используют выбранный на клиенте actor_id; его подлинность не подтверждена сервером. Реальные персональные данные и служебные СОП не размещать до согласования предприятия, авторизации и защиты хранения. Не отправлять письма без разрешения и проверенного адреса. Не добавлять второй каталог сотрудников.

## LC8.1 — учётные записи и права

- Раздел «Управление центром → Пользователи и права доступа»: создать аккаунт/выдать пароль/заблокировать, сброс доступа, привязка к существующему person.id (один активный аккаунт на сотрудника), несколько ролей, область подразделения; поле корпоративной почты — проверяемый адрес, не обязательный для всех сотрудников.
- Серверная учётная запись с собственным неизменяемым ID, пароль с современным стойким salted KDF (scrypt/Argon2id) или согласованный корпоративный SSO. Не хранить пароли/токены в общей SQLite-копии/событиях/логах. Сессии с Secure/HttpOnly/SameSite cookie, сроком, ротацией, отзывом; CSRF, ограничение попыток, безопасная активация и восстановление. Никакой самостоятельной регистрации неизвестных лиц. Bootstrap администратора только через секрет, без заводского пароля. Единый существующий справочник business_role и role_assignment; серверные permission/grant/scope привязаны к его ID, без второго видимого справочника. Назначение бизнес-роли само по себе не выдаёт доступ: требуется подтверждённый грант.
- Минимальные роли: администратор, управляющий центром TWI (максимальные операционные права без администрирования), разработчик СОП, согласующий, наставник/ВТ, руководитель подразделения, сотрудник, наблюдатель. Матрица CRUD+действия+scope по сущностям; сервер проверяет доступ на каждый маршрут и событие, actor_id из сессии, время решения — серверное. Персональные/ограниченные данные не должны попадать в полный снимок для сотрудника: требуются серверные проекции или иной проверенный scoped transport, а не фильтр UI. Старый полный snapshot запрещён ограниченным аккаунтам. Кэш разделён по стабильному account ID; отзыв, очистка локального кэша и политика offline определяются с IT. Тесты на чтение чужого, подмену actor_id, смену ролей, отозванную сессию, повтор пакета, прямой HTTP, не только кнопки. Миграция демонстрационной базы и откат проверяются на копии.

## LC8.2 — личное рабочее место и уведомления

- Колокольчик в шапке, число непрочитанных, список «Все / Непрочитанные / Требуют действия», дата, ссылка на исходную карточку; действия «Прочитано»/«Отметить все». «Мой план» и существующие задачи/календарь остаются источниками истины, не дублировать журнал заданий. Прочитано != выполнено. Проверить мобильный UI, доступность с клавиатуры, пустое состояние.
- Сервер формирует уведомление после подтверждённого доменного события, адресует account/person, сохраняет историю и read_at отдельно для каждого получателя. Уникальный ключ event_id+recipient+type; транзакция с доменным изменением или подтверждённый идемпотентный outbox/reconciliation. Никаких уведомлений от отклонённых/локальных событий. Загрузка только своего inbox, включая count; клиентское обновление по текущему механизму обмена, без обязательных WebSocket. Ссылки проверяют права, не содержат токенов.
- События: назначение/изменение/отмена задачи, срок и просрочка, инструктаж/обучение/переобучение, результаты аудита и оценок для уполномоченных, назначение согласования, возврат, согласование, ввод в действие, срок пересмотра СОП. Напоминания рассчитываются сервером по согласованному business clock/часовому поясу с дедупликацией по сроку; при недоступности связи не терять назначения. Ограничение повторов, настройки типов и каналов. Данные задачи/документа читаются из исходного модуля; не копировать содержимое в уведомления без необходимости.

## LC8.3 — согласование СОП по пользователям

- Сохранить проверенные статусы, проверки заполнения, неизменяемость действующей версии, каталог и связанные ФРВ/TWI. Добавить маршруты согласования для конкретной ревизии и хэша: этапы, согласующие из каталога с активной учётной записью/правом, сроки, обязательность, последовательный или параллельный этап; фиксировать состав на отправке.
- Разработчик отправляет черновик, назначенные получают задачи и уведомления; «Мои согласования» — фильтр существующих задач/документов. Решение только от назначенного авторизованного лица; согласовать/вернуть с причиной, комментарий; запрет самосогласования по умолчанию, замещение только по утверждённому правилу. Обязательные согласования ОТ, главного инженера, ВТ; после них «Согласован / ожидает утверждения», отдельное утверждение директором, затем ввод в действие по принятому порядку. Возврат прекращает текущий цикл; повторное согласование новой версии/хэша, старые решения остаются в истории. Не путать с юридически значимой ЭП; при необходимости отдельное согласование с предприятием.
- Атомарно фиксировать решение, actor/account, revision/hash, server timestamp, комментарий, результат перехода и уведомления. Сервер проверяет все условия, в том числе повтор/конкурентное решение, подмену ID, изменение СОП после согласования, замещение. Тесты: два автора/два согласующих, запрет третьему, возврат, повторная отправка, согласование всех этапов, ввод в действие, уведомления и история, старая версия сохраняется.

## LC8.4 — почтовый канал

- Не рассылка из браузера/ИИ-прокси. Настройка разрешённого корпоративного SMTP relay (TLS, выделенный отправитель) или согласованного HTTPS почтового API (например Yandex Cloud Postbox). Возможность подключения корпоративной сети/исходящих портов Amvera и политика IT проверяются отдельно; HTTPS API не требует SMTP-соединения с Amvera. Секрет только на сервере/в Amvera, не в базе клиента. Источник адресов — проверенные рабочие адреса. По умолчанию email выключен.
- Почта — дополнительный канал того же inbox, а не отдельная бизнес-логика. Durable outbox с idempotency key, retry/backoff, ограничением частоты и числом попыток, временем следующей попытки, журналом доставки/ошибок, безопасным повтором. SMTP не гарантирует exactly-once при потерянном ACK: состояние неопределённости и ручной контроль вместо бесконечной рассылки. Важные назначения сразу; сводка/напоминания — по настройке. В письме минимум сведений, ссылка на HTTPS с обычным входом, без токенов, фото, ФИО третьих лиц и оценок. Mail failure не блокирует сохранение задачи/СОП.
- Админ-настройки, тест только на подтверждённый учебный адрес, лог без секретов. SPF/DKIM/DMARC и отправитель согласуются с IT; не обходить корпоративные ограничения. Тесты mock, повторы, перезапуск очереди, отозванный доступ, невалидный адрес, недоступный SMTP/API, отказ одного получателя, предотвращение дублей. Реальное письмо — только по отдельному разрешению владельца.

## Приёмка и развёртывание

LC8.1 является обязательной основой LC8.2/3, затем LC8.4. Каждая интеграция использует существующее доменное ядро и схемы, миграции тестируются на синтетических данных и резервной копии. Все этапы вместе проходят полный месячный сценарий, серверные проверки разграничения, восстановление и мобильный UI. Не заявлять промышленную готовность по факту запуска demo. Не подключать новые ветки к живому Amvera автоматически. Тариф и один writer сохраняются до подтверждённой потребности. Не отправлять пользователям реальные приглашения/письма в процессе тестирования.
