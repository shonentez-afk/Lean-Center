## Контракт D1

- Единственный источник фактов — прежние таблицы рабочих процессов и change_event. Внутри общего защищённого mutate transaction запоминается последний rowid change_event и после успешной команды проецируются только добавленные события. lc824_domain_notice хранит ID факта, объект, тип, адресата, действовавшее кадровое назначение и отметку прочтения. Не является вторым реестром задач, не копирует оценки, фотографии, документы или статус работы. Отмена транзакции отменяет и уведомление. Отсутствие нового события не создаёт уведомлений. Начальная миграция и восстановление не переигрывают историю.
- TWI: только факт окончательного согласования даёт рабочее уведомление обучаемому; черновик/первый голос не является подтверждённым поручением. Перенос срока и отмена — информационные события; новый раунд согласования возвращает активность. Старое назначение не получает призыв начать обучение после замены СОП. Существующее B-напоминание о сроке не является разрешением на работу.
- Календарь: адресат аудита, практической оценки или самооценки — owner_id. Перепланирование связано с новым планом, отмена сохраняет историю. Факт оценки закрывает соответствующий план по прежней процедуре регистрации, а не по прочтению уведомления.
- Результат аудита — проверяемый наставник; практической оценки — оцениваемый сотрудник. Только если есть право открыть исходную карточку и действующее кадровое назначение. Аннулированные факты не выдаются как действующий результат.
- Мероприятие — owner_id. Проверка, неэффективность, отмена показывают актуальное состояние исходной карточки. Нет массовой рассылки руководителям. Получение/прочтение не закрывает задачу, не создаёт допуск. Старое событие по тому же объекту сохраняется в истории, но не остаётся отдельной активной обязанностью.
- Нет доступа к чужому объекту по notification ID. Повторно проверяются владелец, кадровое назначение, существующий recordAccess (read+detail), состояние источника. Поздний аккаунт видит только всё ещё актуальное назначенное ему поручение, не закрытую историю. Для старого аккаунта права на исторические записи не расширяются. При переводе прежняя адресная проекция скрывается; новый ответственный определяется существующими бизнес-процессами, а не автоматически системой уведомлений.
- Единый API notifications, три внутренних источника (LC8.3 оригинальные, LC8.2.2 фоновые, LC8.2.4 доменные). Снимок read-all v3 учитывает три независимых порядковых номера; сохраняется приём UUID и v2 из A/B. Новые записи после снимка не отмечаются прочитанными. Третий device watermark domain_after добавляется совместимо: старые устройства имеют 0, потому что до D1 источника не было; новые получают текущий порядковый номер. Повторное включение администратором обновляет все три отсечки. Категории training, audit и task теперь используют те же настройки, очередь и recheck перед отправкой. Наружу только общий текст; ключи и данные закрыты. Устаревший assignment не является поводом для внешней доставки.
- Производительность: для карточки и смены статуса отдельного мероприятия переиспользован исходный actionRows с точным условием id, не загружается весь журнал только ради одной карточки. Не изменены алгоритм actionStatus, критерии эффективности, 20 вопросов L1, правила TWI и допусков.
