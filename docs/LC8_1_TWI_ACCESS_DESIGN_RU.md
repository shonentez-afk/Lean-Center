## Уточнение LC8.1: выдача паролей на этапе испытаний

Последнее решение владельца: в первом испытательном варианте администратор задаёт/генерирует индивидуальный пароль при создании учётной записи и передаёт его сотруднику. Сотрудник сразу входит с выданным паролем. Обязательная смена при первом входе, самостоятельная смена/восстановление и отдельная функция смены/сброса уже выданного пароля администратором пока не включаются. Архитектуру административной смены/сброса и соответствующие проверки, описанные ниже, сохраняем как требования будущего включения без изменения account_id, ролей или истории. До отдельного решения владельца соответствующие действия не доступны в UI и API; одного скрытия кнопки недостаточно. Хэширование, проверка прав, ограничение попыток входа и блокировка аккаунтов сохраняются. Не использовать реальные корпоративные пароли и персональные данные на демо-стенде. Уточнение требований, не реализация авторизации.

## Будущее расширение LC8.1: смена и сброс пароля администратором (пока отключено)

В архитектуре предусмотреть для последующего включения действие «Сменить / сбросить пароль»: администратор вводит новый пароль с подтверждением либо генерирует стойкий пароль на сервере; знание старого пароля сотрудника не требуется. Новый пароль выдаётся лично/по согласованному защищённому каналу и показывается только при выдаче. После успешной атомарной записи нового хэша старый пароль и все прежние сеансы данного аккаунта недействительны. Сохраняются account_id, person_id, логин, назначения, роли, область доступа, статус блокировки и история; сброс не разблокирует аккаунт и не повышает права. Проверять право account.password.reset, границы полномочий и недавнюю повторную аутентификацию администратора; защитить сброс привилегированных аккаунтов от обхода разделения полномочий, исключить смену пароля через обычный CRUD/импорт. Аудит: инициатор, целевой аккаунт, время, результат, без паролей/хэшей/токенов. После будущего включения сброса в demo новый пароль работает сразу, без обязательной смены при первом входе; серверная политика смены при выдаче/сбросе предусмотрена для последующего включения. Приёмочные тесты: новый пароль принимается, прежний и старые сеансы отвергаются, неадминистратор получает отказ, заблокированный аккаунт остаётся заблокированным, данные и права сохраняются, ошибки записи не оставляют частично изменённое состояние, секреты не выдаются в списках/журналах. Это требования к LC8.1, не готовая функция на текущем Amvera.

## 2. Переиспользование справочника ролей (уточнение владельца)

Один видимый справочник «Роли сотрудников» — business_role (id, code, name, archived, rev) из db/migrations/003_lc2.sql. Уже существует role_assignment (person_id, role_id, valid_from, valid_to, rev), история, запрет пересечения одной роли, проверка архивирования; people-directory.js показывает действующие назначения. Существующие доменные правила не менять: LC4/LC6 используют квалификации, приказы, допуски (mentor_credential, mentor_appointment, mentor_authorization), а не логин.

Не заводить второй каталог ролей сотрудников. В существующем справочнике добавить вкладки «Описание», «Права в системе», «Назначения», «История». Только уполномоченный администратор меняет права. Системные роли, если ещё отсутствуют (например, администратор доступа), добавлять в тот же каталог с устойчивым ID и признаком системной роли. Не определять права по совпадению ФИО или названия должности. Внутренние таблицы server-only permission, role_permission, account_access_grant, scope, policy_revision — технические связи с business_role.id, а не ещё один справочник ролей. Существующие role_assignment не превращаются автоматически в привилегии. Импорт/изменение доменного назначения не выдаёт права; администратор подтверждает доступ на основании действующего назначения. Grant привязан к аккаунту, роли, назначению/основанию, области, сроку, выдавшему, версии политики. Закрытие/архивирование назначения отзывает связанный grant, а не стирает историю. Для системной роли допустимо отдельное подтверждённое системное назначение. Существующие роли без аккаунта/гранта продолжают работать как профессиональные назначения. Один аккаунт может иметь несколько ролей, каждая со своей областью. Пользователь с правом кадрового редактирования не может повысить свои системные полномочия.

## 3. Организация пользователей

Раздел «Управление центром → Пользователи» и вкладка «Доступ к системе» в карточке сотрудника. Выбор из существующего каталога person; ФИО, должность, подразделение, смена подставляются. Стабильный account_id связан с person.id, не с изменяемым логином. Один действующий аккаунт на человека; у сотрудника может не быть аккаунта. По решению владельца в первой версии администратор создаёт учётную запись, подтверждает роли и области, выдаёт начальный пароль лично или по согласованному защищённому каналу. Основной логин — рабочая почта, при её отсутствии уникальный индивидуальный логин (возможно табельный номер с префиксом площадки). Почта необязательна; логины уникальны после нормализации, изменение логина не меняет account_id. Пароль задаётся администратором либо генерируется системой с проверкой стойкости и показывается только при выдаче/сбросе. По решению владельца в испытательном режиме обязательная смена при первом входе отключена: сотрудник сразу входит с выданным паролем и получает только назначенные права. Не требуется автоматическое истечение начального пароля на испытательном стенде. Предусмотреть серверную политику обязательной смены при первом входе/сбросе, включаемую перед промышленной эксплуатацией без миграции аккаунтов и изменения модели прав; production не должен неявно наследовать послабления demo. При включённой политике до смены доступны только смена пароля и выход. Пароль Центра TWI отдельный от корпоративного пароля. Повторная выдача отзывает предыдущий пароль и сеансы. Администратор не может прочитать установленный сотрудником пароль, только сбросить и выдать новый пароль. Храним только стойкий salted KDF, не plaintext; пароль не включать в журналы, выгрузки, уведомления. Статусы: активен, заблокирован, архивирован; состояние обязательной смены пароля применяется только при включённой серверной политике. Поиск по сотруднику, роли, подразделению, статусу. История остаётся после увольнения; перевод меняет актуальные права после проверки. Защита последнего администратора; повышение привилегий с отдельным подтверждением, аудит. Открытая регистрация и ссылки приглашения не требуются в LC8.1; самостоятельное восстановление через проверенную почту и корпоративный SSO оставлены как будущие расширения.

## 4. Права, область и квалификация

Единый серверный authorize(principal, action, resource, context), default deny. Разрешение = одна подходящая подтверждённая связка роль+область+действие, актуальная на момент операции, плюс отношение к объекту, состояние и доменные условия. Не смешивать scope одной роли с permission другой. Scope: предприятие/цех с дочерними/участок/смена/назначенная операция/конкретная запись/свои данные. Для ВТ/инструктора/наставника действующая квалификация/приказ/допуск остаются обязательными где это требует домен; системная роль сама по себе не сертификат. Одна должность может сочетать несколько ролей. Временное замещение — с основанием, сроком, явным разрешением, аудитом; не передача логина. Админ доступа не получает право согласовывать/утверждать документы по факту администрирования. Настраиваемые permissions по модулю, чтению, созданию, изменению, workflow, экспорту, истории, отдельным чувствительным полям и финансовым данным. Нельзя обойти обязательные проверки настройкой роли.

### Управляющий центром TWI — максимальный операционный профиль

Уточнение владельца: это второй по объёму возможностей профиль после администратора, не отдельное приложение и не второй справочник ролей. Ранее названный «Руководитель центра TWI» является этим же профилем: использовать один стабильный ID существующей подходящей business_role либо добавить отсутствующую роль после явного сопоставления, не создавать дубль по названию. Область по умолчанию — всё назначенное предприятие с дочерними подразделениями, участками и сменами. Между предприятиями доступ только при явном назначении.

- Чтение: все операционные разделы центра, включая карточки сотрудников и их рабочие назначения, каталог и конструктор СОП, черновики и архив, историю согласования, ФРВ, TWI, программы и факты обучения, матрицы, наставников и ВТ, сертификацию, аудиты и оценки, задачи, календарь, отчётность, ROI и предусмотренные центром сведения о доплатах. Доступ к рабочим данным центра не означает доступ к секретам, паролям, личным уведомлениям других аккаунтов или данным за границами предприятия.
- Работа: создание и редактирование разрешённых рабочих записей, управление планами, назначение ответственных и задач, контроль сроков, ведение рабочих справочников и бизнес-настроек, формирование и экспорт разрешённой отчётности. Сохраняются все доменные проверки, история и неизменяемость подтверждённых фактов и действующих редакций. Для операций с персональными и финансовыми данными действуют согласованные с предприятием правила экспорта.
- Исключено из роли: создание/блокировка аккаунтов, выдача и сброс паролей, отзыв чужих сеансов, выдача системных прав и областей доступа, изменение permission-политик, изменение защищённых привилегированных назначений, управление секретами, почтовыми ключами, настройками сервера, резервными копиями и восстановлением, удаление журналов безопасности. Разрешено видеть бизнес-роли и кадровые назначения, но их изменение не должно повышать системные полномочия; защищённые назначения требуют отдельного подтверждения.
- Управляющий видит весь ход согласования СОП, может организовывать маршруты в рамках обязательного шаблона, контролировать сроки и готовить документы. Не может вместо назначенных руководителя ОТ, главного инженера, ВТ и директора принять их решения. Только отдельное подтверждённое полномочие, фактическая квалификация, область и назначение разрешают конкретное действие. Не предоставлять обход самосогласования или изменение подписанной ревизии. Те же ограничения сохраняются для допуска к работе, подтверждения навыков и аудита.
- Реализация: явный версионированный набор разрешений максимального операционного профиля, не wildcard «все, кроме admin». Новые модули включаются после классификации прав. Системный администратор управляет доступом, а для полного рабочего доступа может иметь дополнительно роль управляющего. Назначенные полномочия директора и согласующих по-прежнему независимы от административных и операционных прав.

Приёмка: управляющий получает доступ к рабочим данным двух разных участков одного предприятия, включая отчёты и историю СОП; может выполнять разрешённые операции и назначения; не получает системные секреты, чужие сессии и административные функции ни из меню, ни прямым API, ни импортом/редактированием ролей; не может выдать себе полномочия, согласовать за другого, утвердить СОП без полномочия директора, менять неизменяемые факты или видеть соседнее предприятие. Проверить все модули и экспорты отдельно.

## 5. Интерфейс

Сохраняем имеющиеся пункты «Роли сотрудников» и «Назначения ролей». Права редактируются в карточке роли; назначение доступа — из карточки пользователя. Показывать итоговые разрешения и область, причину недоступности действия, историю выдачи/отзыва. «Мой план» уже есть — персональная выборка из сессии; персональная шапка, уведомления, согласования и задачи. Для директора — очередь утверждения; ВТ — обучение/аудиты; инструктора — свои операции/ученики; руководителя — его подразделение; сотрудника — компактный личный кабинет. Разделы скрываются по правам, но скрытие не механизм безопасности.

## 6. Контракт согласования СОП для LC8.3

Сохранить document/document_revision/document_approval, версии, проверки качества, ФРВ/TWI, неизменяемость действующей редакции. Сейчас один approve и ручной actor_id; этого недостаточно.
Новый маршрут: черновик → согласование ОТ, главного инженера и ВТ (предложение: параллельно; последовательность настраиваемая) → «Согласован, ожидает утверждения» → отдельное действие директора «Утвердить» → «Утверждён» → ввод в действие уполномоченным лицом согласно принятому порядку. Все три обязательны; директор не заменяет согласующих. Возможность одной кнопки «Утвердить и ввести в действие» только как два проверенных перехода. Фиксировать версию маршрута, назначенных участников и роль, идентификатор ревизии и хэш значимого содержания/реквизитов/вложений; серверный актёр и время, результат, замечания. При возврате — причина и новый раунд после исправления. При изменении содержания/значимых реквизитов или состава — старые решения не переносятся. Запрет самосогласования по умолчанию, замещение только по подтверждённым правилам. Сотрудник видит прежнюю действующую версию до ввода новой. Согласующие получают доступ к назначенной ревизии, а не всей библиотеке. Не считать вручную заполненную строку «Согласовано» импортированного документа электронным решением; не имитировать подпись. Старый approved не означает утверждение директором. Юридический статус электронного решения и возможная регистрация бумажного утверждения — по отдельному согласованию. После ввода — адресные задачи ознакомления/обучения; не считать ознакомление допуском.

## 7. Архитектурная граница и безопасная миграция

Нынешний LC7.4.6 передаёт полную SQLite v17 каждому editor/viewer и принимает generic пакеты с клиентским actor_id. Нельзя включить реальные ограниченные аккаунты поверх такого API. Выбираем один сервер Node/один writer, одну каноническую доменную базу и прежние доменные валидаторы. Слой auth/session → policy → scoped query/command → domain validation → durable commit/audit/outbox. Серверные таблицы авторизации и секреты никогда не входят в клиентские/автономные выгрузки. Проверить протокол атомарности и миграции service schema, не разделять бизнес-данные между ролями. Для ограниченных пользователей перейти к серверным проекциям/командам; полный snapshot и произвольные клиентские пакеты запрещены в secure mode. Инвентаризировать все маршруты и события до переключения; неизвестные запрещены. Не переписывать принятые экраны и вычисления без необходимости, выделить слой доступа к данным. Ограничить исходники, вложения, справочники выбора, экспорт, аналитику/детализацию и ИИ. Для первого защищённого режима выбирать online-first, не выдавать полную базу на диск, no-store, без новых офлайн-копий чужих данных. Старые демо-кэши не считать безопасными и не импортировать автоматически. Сохранение LC7.4.6 опирается на фактическое подтверждение сервером; при обрыве защищённого режима локальный черновик/повтор только после проверки права и ревизии, без сохранения токенов и лишних данных. Отзыв не может гарантированно удалить уже скачанные файлы. Разрешённые экспорты/локальное хранение и реальная эксплуатация согласуются с IT.

Аутентификация: локальные учётные записи с scrypt/Argon2id, индивидуальная соль, ограничение попыток и срок сессии, защищённая cookie HttpOnly Secure SameSite, CSRF, отзыв и ротация сессий, повторная аутентификация для критических действий; OIDC/SSO и MFA как предусмотренные расширения (для привилегированных пользователей до промышленной эксплуатации — согласно политике IT). Bootstrap администратора только одноразовым серверным секретом; не оставлять legacy токены действующими обходными путями в secure mode. Смена роли/увольнение проверяется при каждом запросе и в момент commit. Не выдавать секреты в UI, логах, экспорте. Резервное копирование авторизации и домена согласовать и проверить; восстановление не должно неожиданно возвращать отозванные сессии.

## 8. Контракты для будущих этапов

Уведомления: подтверждённые domain events → идемпотентный outbox → личный inbox (account/person, источник, право доступа, read_at, требуемое действие). Не дублировать задачи. Чтение != исполнение. Личный счётчик в шапке. Email — дополнительный канал того же события, проверенный адрес, отправитель/SMTP/API только после согласования, durable retries, без токенов/чувствительных данных. Разграничить разрешения на чтение и доставку; при отзыве доступа прекратить выдачу/доставку. Никаких реальных писем в тестах. Согласования и назначения используют тот же account/person/role/scope/policy, а не отдельные пароли и справочники.

## 9. Приёмка LC8.1 и последовательность реализации

Сначала инвентаризация всех экранов/действий, таблиц и actor fields → таблица покрытий. Затем серверные контракты auth+ACL и миграция на изолированной копии → управление пользователями/расширение имеющихся ролей → персональные ограниченные запросы/команды всех существующих функций → проверка. Не подключать LC8 к работающему стенду до полного PASS.
Минимальные тесты: один сотрудник с несколькими ролями и разными областями; два участка; директор, три согласующих, ВТ, инструктор, наставник, сотрудник, администратор; отказ доступа к чужим строкам/файлам/агрегатам/экспорту; подмена actor_id, scope и ID; запрет самоэскалации через реестр/импорт; истечение/закрытие назначения, блокировка сессии и повтор запроса, перевод; неизвестные действия запрещены; отсутствие секретов и полной базы в браузере; повтор команды и конкуренция; резервное восстановление, старые данные и история; отсутствие регрессии СОП с фотографиями, ФРВ, TWI, матриц, аудита, доплат, ROI и печатных форм; мобильные сценарии. Затем LC8.2 уведомления, LC8.3 согласование СОП, LC8.4 почта. Не считать архитектурный документ готовой авторизацией.
