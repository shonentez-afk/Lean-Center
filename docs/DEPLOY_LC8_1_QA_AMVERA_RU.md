# Отдельная QA-ветка Amvera LC8.1

Ветка `feature/lc8.1-amvera-qa` подготовлена на основании принятого автоматическими тестами кандидата `292a762` (Actions 45940860407 SUCCESS). В ней корневой `amvera.yml` уже является точной копией `deploy/lc81-amvera/amvera.yml`. Карта `tools/cloud-source.json` закреплена отдельным метаданным коммитом, контроль целостности не отключён. Ничего вручную копировать и менять перед сборкой не надо. Ветка не подключена к Amvera; main, интеграционная ветка и действующий сервер не меняются.

CI этой ветки выполняет стандартный набор LC8.1 и новый локальный тест защищённого рецепта: проверка полного дескриптора, /healthz, отказ legacy API, Origin и сессия, инициализация временного тома, контрольная запись, перезапуск без начального секрета, отдельные backup/restore-new и отказ перезаписи. Это только локальная имитация, не проверка внешнего прокси/постоянного тома Amvera. До отдельного стенда и подтверждения владельца DEPLOY-01 остаётся открытым для эксплуатации. Кнопка «Проверить AI» и предметный код не изменены.

## Параметры испытательного экземпляра

- Одна реплика, Node 22, npm, порт 8080. Отдельный новый постоянный том /data.
- LC81_QA=1, LC81_DATA_DIR=/data/lc81-qa (новый отдельный каталог), LC81_ORIGIN=https://<точный-HTTPS-домен-без-завершающего-слеша>.
- LC81_INIT=1 и секрет LC_BOOTSTRAP_ADMIN_PASSWORD только для первичной инициализации; LC_BOOTSTRAP_ADMIN_LOGIN при необходимости. Пароль не хранить в Git/логах/скриншотах. После инициализации убрать флаг и начальный секрет, проверить сохранённый аккаунт после рестарта.
- LC81_SITE_TIME_ZONE — только подтверждённая IANA-зона предприятия при первоначальном запуске/миграции; существующую зону не менять. LC81_CLOUD_AI отсутствует либо 0. LC_PILOT_DEMO и LC_PILOT_USERS не передавать.
- Только учебные данные или отдельно согласованная изолированная копия. Никогда не указывать путь к legacy или действующему рабочему томy.

## Проверка старта и защиты

1. Проверить CI и точный исходный SHA. Убедиться, что приложение связано с отдельным QA-томом и правильной точкой входа.
2. Внешний HTTPS /healthz должен вернуть ok:true, mode:"LC8.1-QA", complete:false и sourceCommit из tools/cloud-source.json. UI должен показать защищённый вход и идентификатор исходника. Legacy API /api/v1/ недоступен, защищённый /api/lc81/session без cookie возвращает 401; cookie Secure, HttpOnly, SameSite=Strict. Неверный Origin для записи отклоняется.
3. Проверить обычные входы нескольких сотрудников за общим прокси, ошибки пароля, 429/Retry-After, 8 одновременных чтений и записи. Сверить выбранную нагрузку с ресурсами площадки: текущие локальные результаты не гарантируют пропускную способность. Не увеличивать защитные лимиты без измерений и согласования.
4. Проверить роль с личным планом, ограниченного аудитора, отзыв одного гранта из двух и открытые вкладки; при возвращении данные скрываются до проверки. Провести полную приёмку корпоративных ролей и контрольных документов.
5. Завершить работу пользователей и очередь сохранения, штатно остановить экземпляр, сделать копию в новый отдельный каталог через LC81_QA=1 node server/lc81-maintenance.mjs backup /abs/source /abs/new-backup. Проверить отдельное restore-new в новой папке и сверить данные/хеши. Не удалять том или writer.lock по возрасту; при аварии сначала подтвердить остановку и получить копию. Проверить возможность выгрузки резервной копии из хостинга до эксплуатации.
6. При отказе остановить только новый QA-экземпляр. Не переключать текущий Amvera, не перезаписывать его хранилище. Любое рабочее внедрение и откат согласовываются отдельно.

Этот документ является рецептом и планом проверки, а не доказательством выполненного развёртывания.

На хостинге сохранялся устаревший run.scriptName: server/main.mjs. В этой ветке оба рецепта приведены к фактическому формату, но с обязательной защищённой точкой входа server/lc81-main.mjs. Пин обновлён. Допускаются только эквивалентное форматирование и документированное написание environment: node. Все поля, включая singleton: true и zeroDowntime: false, проверяются; дополнительные команды, старый запуск, неизвестные/повторные ключи, другой порт, каталог хранения и иные значения отклоняются. В CI добавлены сценарии фактического YAML и отказа старой конфигурации. Остальные исходники проверяются побайтово. Не удалять Data; сохранить нужные локальные файлы Code перед синхронизацией. В Amvera проверить точное значение scriptName и выбрать ветку feature/lc8.1-amvera-qa. Реальный результат сборки и запуска на хостинге ещё требует подтверждения. Переменные и пароль администратора не менять.

## Перезапись package-lock.json при установке npm на Amvera

Фактическая сборка Amvera 27.11.2026 прошла проверку amvera.yml, но остановилась на несовпадении package-lock.json: ожидался fbd4296b227f2da04badeecfb2a8b659983ae11d, получен 5b074f210ba48d6158682a3c724250c9b89f45a5. Точное содержимое изменённого файла не предоставлено; вероятная причина — автоматический npm install до additionalCommands. В отдельной QA-ветке добавлена побайтовая копия исходного lock в tools/lc81-amvera-package-lock.json с таким же закреплённым git blob SHA. Перед импортом esbuild и других npm-модулей сборка проверяет весь набор исходников и защищённый рецепт; только при подтверждённой канонической копии восстанавливает корневой lock. Затем выполняет npm ci --ignore-scripts --include=dev --include=optional --package-lock=true --no-audit --no-fund и повторно проверяет все контрольные суммы. Не принимает новую версию зависимости из файла хостинга. Другие расхождения остаются ошибками. CI искусственно меняет версию зависимости в корневом lock перед настоящей облачной сборкой и проверяет восстановление исходника, а отдельный тест проверяет отказ при подмене канонической копии или package.json. Это контроль нашей сборки, не утверждение о содержимом изменённого файла хостинга. Код и команда Amvera, переменные, база данных и кнопка «Проверить AI» не изменены. При обновлении зависимостей в этой ветке необходимо одновременно обновлять обе копии lock и карту исходников. После успешного Actions выполнить синхронизацию этой ветки и повторную сборку; Data не удалять.

## Диагностика отказа первого запуска (27.11.2026)

После устранения ошибок сборки сервер на Amvera отказался запускаться. Причина старого общего сообщения не установлена. Новый entrypoint выполняет проверку режима, HTTPS origin и параметров до открытия хранилища и пишет только фиксированный код, без значений переменных, путей, паролей и текста произвольных исключений. Основные коды: QA_MODE_REQUIRED (LC81_QA=1), LEGACY_ENV_PRESENT (удалить LC_PILOT_DEMO=1 и непустой LC_PILOT_USERS), ORIGIN_INVALID (реальный HTTPS origin без слеша, пути, логина или query), DATA_PATH_INVALID (отдельный абсолютный путь), DATA_PARENT_MISSING (отсутствует родительский каталог, проверить подключение тома), INIT_REQUIRED (LC81_INIT=1 для нового каталога), BOOTSTRAP_LOGIN_INVALID и BOOTSTRAP_SECRET_INVALID (начальный логин и пароль от 12 до 128 байт), STORAGE_LOCK_PRESENT (не удалять writer.lock: сначала подтвердить остановку всех процессов), STORAGE_INCOMPLETE (существующая папка без полного снимка и маркера; не инициализировать поверх неё), STORAGE_SIZE_INVALID/STORAGE_CHECKSUM_INVALID (проверить резервную копию). STORAGE_PREFLIGHT_*, STORAGE_OPEN_* и HTTP_LISTEN_* с системным кодом уточняют этап и тип ошибки. Например, EACCES/EPERM — права, EROFS — том только для чтения, ENOSPC — место, ENOENT — отсутствующий файл, EADDRINUSE — порт занят. Для действующего хранилища начальный секрет не требуется. Тест проверяет отказы, отсутствие секретов в журнале и сохранение существующей папки и lock-файла. Ни автоматического удаления, ни сброса пароля, ни повторной инициализации поверх данных нет. Пришлите код из нового журнала Amvera, не присылайте значения секретов. Фактическую причину установим по коду, не по предположениям.

## Первый вход и настройка пустого предприятия (27.11.2026)

После запуска на Amvera получен отзыв: у администратора и управляющего почти пустые разделы, конструктор не открывается до создания операции, в справочнике ролей нет кнопки создания. Первичная инициализация создаёт только системного администратора, корень предприятия и две защищённые роли. Она не переносит предыдущую базу и не создаёт вымышленные производственные данные. В текущем кандидате добавлена панель настройки центра, прямое создание ролей администратором из справочника, подсказки о кадровых назначениях и подтверждении доступа. СОП и ФРВ можно открыть/импортировать как рабочую копию без заранее выбранной операции. При сохранении выбирается существующая разрешённая операция; пользователь с правом operation.create может указать новую операцию с подразделением, кодом и названием. Новая операция и черновик сохраняются в одной транзакции; ошибка документа не оставляет лишнюю операцию, повтор запроса идемпотентен. Обычный сотрудник не получает дополнительных прав на операции или роли. Если нет ни одной доступной операции и нет права создания операции, сохранять непривязанный черновик нельзя. Роль управляющего должна быть назначена реальному сотруднику и иметь подтверждённый доступ с областью всего предприятия. Системный администратор без карточки сотрудника не выполняет личные производственные решения. Старые данные сохраняются в прежнем каталоге и требуют отдельного согласованного переноса, не инициализации поверх существующей базы. Изменения проверяются на новых синтетических данных в CI. Код «Проверить AI» не менялся. До подтверждения CI и проверки интерфейса на Amvera приёмка не завершена.

## Первый старт и администрирование v2; ИИ конструктора Stage43

В защищённом интерфейсе добавлены отдельные пункты «Начало работы», «Предприятие», «Пользователи», «Роли и права», «Назначения и доступ», «Хранение и журнал». Начальный экран показывает реальные количества и состояние настройки, а не вымышленные производственные записи. Мастер пользователя создаёт нового сотрудника с действующим кадровым назначением либо выбирает существующего без аккаунта; по явному выбору управляющего создаёт/использует его рабочую роль и подтверждает доступ ко всему предприятию в той же транзакции. Базовый сотрудник не получает управленческих прав. Отдельное назначение доступа существующему пользователю проверяет роль, её политику, область, срок и историю; недостающая роль и доступ создаются атомарно. Предыдущие назначения, права и бизнес-данные не изменяются автоматически. Управляющий с действующим полным доступом начинает с дашборда, при пустом справочнике операций видит быстрые переходы. Для администратора рабочие группы свернуты по умолчанию. Изменения сохраняют старые серверные маршруты, аудит и все ограничения на личные производственные решения.

В реальном журнале Amvera выявлены CSP-отказы старых прямых запросов Stage43 к Yandex Cloud. HTTP 401 на /api/lc81/session до входа — штатный ответ; если 401 после входа, проверять сессию отдельно. Для LC8.1 восстановлен транспорт aiAsk через родительское окно и серверный POST /api/lc81/editor/ai. Исходный Stage43, кнопка «Проверить AI», модели, системные промпты, схема ответа и проверки применения результатов сохранены. Opaque sandbox и connect-src data: blob: не ослабляются. Администратор размещения должен отдельно разрешить отправку текста редактора во внешний сервис: переменная запуска LC81_EDITOR_AI=1, по умолчанию отключено. Это не LC81_CLOUD_AI (общий помощник центра с прежней ограниченной отправкой). Включение LC81_EDITOR_AI разрешает каждому авторизованному пользователю с доступом к редактируемой рабочей копии использовать ИИ конструктора; каждое обращение с содержимым требует подтверждения точного текста и политики организации. Проверка подключения по старой кнопке передаёт только два фиксированных тестовых сообщения, без документа; сервер проверяет точный пакет. Адрес прокси фиксирован, переадресация и передача cookies запрещены, размеры, модели, типы задач, время и частота ограничены; права на контекст проверяются до и после обращения. При выключенном ИИ редактор не делает сетевых попыток, ручная работа доступна. В CI внешняя сеть заменена синтетическим ответом; проверяются отказ без доступа/подтверждения, отдельный флаг, закрытый iframe, точный запрос, отмена в диалоге, оригинальная кнопка и реальный мастер пользователя. Реальную доступность Yandex Cloud и разрешение организации на передачу данных надо подтвердить отдельно. Никакого изменения прокси Yandex, паролей, переменных на Amvera или базы без владельца.

## Готовые рабочие роли и помощник разделов

Кандидат содержит 16 начальных профилей рабочих ролей в существующем business_role, дополнительно к двум прежним системным ролям. Роли и обязанности сопоставлены с принятой версией TWI и ранее согласованной архитектурой LC8.1; конкретные системные permissions являются настраиваемыми проектными профилями, не буквальной таблицей корпоративского стандарта. Чистая QA-база получает каталог ролей и начальные политики без учётных записей сотрудников, назначений, прав доступа или сертификатов. На существующей базе администратор открывает «Роли и права» → «Добавить недостающие роли TWI». Команда добавляет только отсутствующие роли, повторный вызов ничего не дублирует. Существующая роль, сходное название/код, пользовательская политика, архив и конфликт совпадений не перезаписываются. Для совпадающей роли можно вручную заполнить рекомендованные права, просмотреть их и сохранить; прежние гранты при смене версии политики требуют подтверждения. Установка не выдаёт права уже имеющимся сотрудникам. В мастере пользователей можно выбрать готовый профиль, область и для назначенных записей дополнительно собственные записи. Сохранение сотрудника, аккаунта, роли и грантов остаётся одной транзакцией. Для наставника стажировки предусмотрен отдельный тип только для программы стажировки; он не подменяет полномочия инструктора TWI. Непосредственное создание/назначение обучения, подтверждение факта, оценка и допуск по-прежнему проходят доменные проверки и требуют соответствующей связи с сотрудником. Не добавлены права согласования/утверждения СОП до LC8.3. Отдельная область смены/конкретной операции ещё не реализована: профиль начальника смены использует явно выбранное подразделение; не заявлять ограничение по смене.

ИИ-помощник: права assistant.read и assistant.cloud различаются, локальный помощник не требует включённого внешнего сервиса. В заголовках поддерживаемых рабочих разделов появилась кнопка «ИИ-помощник раздела» со списком разрешённых сохранённых записей; в отчётах и карточках сохранён контекстный запуск. Сервер проверяет право и источник каждой записи; персональная/назначенная область учитывается без выдачи доступа к чужим данным. Локальная проверка СОП/ФРВ может использовать уже разрешённую общую библиотеку и собственные черновики, но не чужие черновики, закрытые вложения или исходный JSON. Облачная рекомендация сохраняет отдельную проверку области и отправку только общих тем, без содержимого документов. Для облачного помощника центра отдельно LC81_CLOUD_AI=1; для конструктора по-прежнему LC81_EDITOR_AI=1. Не включать внешнюю отправку без разрешения организации. Проверки: первоначальный каталог, отсутствие автоматических грантов, создание пользователя с профилем, отклонение неверной области без частичной записи, сохранение изменённой политики при повторной установке, персональный помощник и запрет чужой карточки, браузерная навигация помощника. Реальная работа с действующей базой требует проверки после CI. Существующая база, аккаунты, настройки Amvera и кнопка «Проверить AI» не меняются автоматически. Корпоративские первоисточники не публикуются.
